## 3. 真实分析记录暴露的问题（本轮最重要的发现）

真实记录：`records/predictions/records/2026-10-15_20-10-08_BTCUSDT_15m.json`

- 决策：**做空限价单**，入场 81071.21 / 止损 81397.05 / 止盈1 80745.37 / 止盈2 80500.01，模型**自评胜率 50%**
- 模型推理正文里的止损是 **81191**（R:R = 2.72，50% 胜率期望 **+103.03 点**，其自检 §10.3 判「是」）
- 程序为满足「TP1 盈亏比上限 = 1.0」**自动放宽止损**：81191 → **81397.05** ⇒ 风险 == 回报 = 325.84 点，期望 **+0.0000 点**（纯抛硬币）
- 叠加真实成本 0.30%（= 243.21 点 = 止盈距离的 **74.6%**）⇒ 该结构需要 **87.3% 胜率**才不亏

复现：`tests/unit/test_cost_viability.py::test_tp1_rr_cap_widening_destroys_edge`（断言上述数字）+ `python tools/edge_math.py`。

**两个独立缺陷：**

1. **方程判定没有容差 → 零期望方案可以过关。** 实测那组数字（risk 325.8399999999965 / reward 325.84000000001106）在修复前 `0.5×reward > 0.5×risk` 返回 **True**，即抛硬币级方案被判「方程通过」。判定结果实际上取决于浮点噪声，而不取决于策略是否有优势。
2. **方程不含成本。** 0.30% 的双边成本在有杠杆/在 15 分钟级别是决定性变量：止盈距离 0.40% 时，成本吃掉 74.6%，盈亏平衡胜率被推到 87%。
3. 附带发现：模型的 §10.3 自检用的是它**推理文字里的止损价**，而不是它自己输出的 `stop_loss_price` 字段——两者相差 206 点时自检仍然"通过"。

## 5. 台账：让「能不能赚钱」由数据回答

单次回测回答不了"下个月还行不行"。台账的机制：

1. 每次分析写下**可证伪的预测**：方向、入场/止损/止盈、模型自评胜率、**当时快照价**、持仓上限、到期时间。
2. 到期后用真实 K 线**逐根判定**：同根内同时触及止损与止盈时按**最坏情况**（先止损）处理；收益扣除双边成本 0.30%。
3. 与同口径基线对比：用**同样的止损/止盈距离**分别"永远做多/永远做空"，看模型是否真的提供了增量。
4. 样本 < 30 条时明确标注"统计上毫无意义"。

用法：

```bash
python tools/trading_ledger.py record                 # 实时分析并记账（消耗 LLM tokens）
python tools/trading_ledger.py record --as-of=-48h    # 历史快照回放（无未来数据）
python tools/trading_ledger.py resolve                # 结算到期预测（零 LLM 成本）
python tools/trading_ledger.py resolve-redo           # 重算全部已结算条目
python tools/trading_ledger.py status                 # 记分板
python tools/trading_ledger.py backfill               # 补齐早期条目缺失的派生字段
```

### 5.1 首次走查回放（8 个历史快照，as-of = 30~198 小时前，间隔 24h）

| 观察 | 结果 |
|---|---|
| 决策分布 | **7/8 弃单（不下单）**，仅 1 次给出下单方案（做多限价单） |
| 该笔交易结局 | **命中止盈**，毛收益 +0.31%，扣双边 0.30% 成本后 **净 +0.014%**（持仓 3 根） |
| 同口径基线 | 永远做多 +0.014%（与模型一致）/ 永远做空 −0.614% |
| 7 次弃单的同期持有收益 | −3.05%、−0.53%、+1.27%、+0.59%、+0.16%、−0.64%、−1.43%（均值 **−0.52%**，即弃单多数避开了下跌） |
| 成本可行性 | 2 条下单方案 **100% 低于 3× 成本**；止盈/成本倍数均值 1.87× |
| 自评 vs 门槛 | 模型自评胜率均值 **52.5%**，而扣成本所需胜率均值 **73.7%** ⇒ 缺口 **+21.2 个百分点** |

> 样本量：已结算 **1 条**。以上任何结论在统计上都**不成立**，台账自己也这么标注。它的价值在于：随着样本累积（定时任务每小时结算、每 6 小时新增一条），这个缺口会由数据自己给出结论。

**最能说明问题的一行**：那笔唯一命中止盈的交易，毛赚 0.31%，而双边成本 0.30% —— **成本吃掉了 97% 的利润**。

### 12.2 已实施的优化：响应缓存（复用完全相同的输入）

**浪费实证**：21:56 那次「增量分析」在"无新增K线，基于上一轮结论复核"下，输入与上一轮**逐字节相同**，却完整重跑两阶段：耗时 29 s、约 **215k tokens**，结论与上轮一致。

**修复**：`pa_agent/ai/response_cache.py` —— 缓存键 = `sha256(base_url + api 模型 + 全部消息 + system + thinking/effort/max_tokens)`，即"输入指纹"。

- 命中时**跳过网络调用**，把上次输出重放给界面（`raw.from_cache=true`，usage 记 0），日志打印节省的 token 数；
- 配置：`provider.response_cache_enabled`（默认开）、`provider.response_cache_ttl_s`（默认 1800s）；
- 落盘 `records/llm_cache/`（`.gitignore` 的 `records/**/*` 已覆盖），原子写，最多 300 条，TTL 过期即删；
- 任何输入变化（新 K 线 / 改提示词文件 / 换模型 / 改思考档位）都会改变指纹 → 缓存自动失效。

**实测对比（同输入连跑两次，`record --as-of=-120h`）**：

| | 第一次（冷） | 第二次（相同输入） |
|---|---|---|
| 管线耗时 | **42.7 s** | **0.2 s** |
| 进程整体 | 47.6 s | 4.3 s |
| 模型调用 | 2 次真实调用（KV 命中 73.1% / 61.1%） | **2 次缓存命中** |
| Token | 176,529 prompt + 7,214 completion | **0**（日志：节省 67,047 + 109,482 prompt） |

⇒ 重复分析 **提速约 213 倍、零 token 成本**。回归：`tests/unit/test_response_cache.py`（13 项，含"缓存命中时绝不创建网络客户端"的反证测试）。

## 13. 用真实样本回答"能不能赚钱"（批量回放实验）

### 13.1 方法：为什么必须"批量 + 可立即结算"

单点回测回答不了盈亏问题，单次分析更不行。新工具 `tools/ledger_batch.py` 的做法：

1. 在**过去**的时间里均匀取 N 个快照点（默认：过去 9 天，每 12 小时一个）；
2. 每个点用 `--as-of` 回放跑**真实两阶段分析**（真实币安历史行情 + 真实 API）——
   数据接口按 `endTime` 截断，物理上看不到未来；
3. 因为快照点都在 24 小时（96 根 15m）持仓上限之外，**跑完立刻能用真实行情结算**；
4. 汇总：净收益（扣双边成本 0.30%）、胜率 vs 每笔自己的盈亏平衡胜率、
   与"永远做多/永远做空"同口径基线对比、弃单的机会成本、自助法 95% 区间、二项检验。

### 13.2 过程中修掉的两个工具缺陷（都是实测踩到的）

| 缺陷 | 现象 | 修复 |
|---|---|---|
| 无单窗口时限 | 某窗口的 API 请求挂住（客户端超时是 **600s/请求**），整批从 17:48 卡到 18:03 毫无进展 | 每个窗口改为**独立子进程 + 硬时限**（`--window-timeout`，默认 240s）：卡住就丢弃该窗口、继续下一个 |
| 批次标记错位 | 用"全局最新条目"打标记，而 as-of 回放写入的是**过去**时间的条目 → 标记打到了错误的行 | 改为**按预期时间戳±10 分钟就近匹配**（`_find_near`），并据此去重，避免重复烧 token |
| argparse 负值 | `--as-of -108h` 被当成选项 → `expected one argument`，15 个窗口全部失败 | 改为 `--as-of=-108h` 形式 |
| 样本 <2 时的区间 | 自助法返回 NaN，却仍打印"区间不跨 0 ⇒ 正期望" | NaN 时明确打印"样本不足，无法给出区间" |

### 13.3 连续性守卫的审计升级（暴露出的透明度缺口）

`apply_continuity_guard`（`ai/decision_continuity.py:597`）为防止自相矛盾方案，会把订单
**改写为「不下单」并清空全部价格字段**。这本身是正确的拒单行为，但：

- 原始方案随之**永久丢失** → 事后无法回答"守卫这次拦得对不对、模型本来想做什么"；
- 界面只显示「不下单」→ 用户无法区分"模型自己判断等待"和"程序把方案拦掉了"。

修复（三处，均有测试）：

1. `apply_continuity_guard` 改写前把原方案留档到 `stage2["continuity_guard"]`
   （`{applied, reason, original_plan}`；归一化在 schema 校验之后执行，不会触发校验失败）；
2. 台账新增 `suppressed_by_guard` / `suppressed_reason` / `suppressed_plan`，并在
   `resolve` 阶段对**被拦方案做反事实结算**（按同样的止损/止盈跑一遍真实行情）——
   这样能直接量化"守卫是拦对了还是在错杀"；
3. 决策面板新增显眼告警行（`decision_panel.py` 的 `suppressedNote`）：
   「⚠ 程序连续性守卫已把模型方案改写为「不下单」：<原因>（模型原方案：做多 · 限价单 · 入场 …）」，
   由 `main_window._continuity_override_note()` 组装。

测试：`tests/unit/test_continuity_guard_audit.py`（4 项）、
`tests/unit/test_decision_panel_suppressed.py`（3 项），均已加入 CI 门禁。

### 13.4 实验结果（16 个真实窗口，币安 BTCUSDT 15m，2026-10-16）

**样本**：过去 9 天、每 12 小时一个快照点，全部用真实历史行情 + 真实 API 跑完整两阶段分析，
共 16 条（另加 1 条早期手工窗口）。每条都在分析完成当时即用真实行情结算（持仓上限 24 小时）。

| 指标 | 结果 |
|---|---|
| 下单 | **0 笔** |
| 弃单 | **16 次（100%）** |
| 弃单同期持有收益均值 | **−0.471%**（负值 = 弃单避免了亏损） |
| 其中弃单后行情其实上涨 | 8/16 = 50%（错过机会的比例） |
| 硬性中止（validation_error） | 1 次（见 13.5，已修） |

**结论（诚实版）**：

1. **"能不能赚钱"在这批样本里无法回答——因为它一笔都没交易**。要得到 30 笔下单样本，
   按实测下单率（<6%）需要约 500+ 个窗口，成本约 1 亿 tokens 量级；
2. 但**它不交易的选择在这批样本里是对的**：同期持有平均 −0.471%，弃单平均避开了小幅亏损；
3. 与既有证据合起来看，风险主要在**成本**而非方向：扣掉双边 0.30% 后，
   它仅有的下单方案净收益仅 +0.014%（毛赚 0.314% 被成本吃掉 95%），
   且按其自身数字需要 64.6% 胜率、而模型自评只有 52.3%（缺口 12.3 个百分点）；
4. 因此当前形态的合理结论是：**它是一个"以不交易为主"的风险过滤器，
   而不是一台能证明正期望的信号机**。要继续推进，需要（a）更大的样本量，或
   （b）把成本压到 0.05% 量级（更低费率/更大止盈结构），或（c）只在止盈结构
   远超成本的窗口交易（现有成本闸门已在做这件事）。

### 13.5 实验暴露并修复的真缺陷：成本闸门会中止整轮分析

第 13.4 表中那条 `validation_error` 就是它：成本不达标的方案被当作**校验错误**，
模型改不出来时整轮分析以异常结束——用户看到"分析失败"，而不是"这一单不做"。

修复（语义对齐产品的 fail-safe 设计）：

1. `json_validator` 不再把成本可行性计入校验错误（`_check_cost_viability` 停用并注明历史）；
2. 新增 `stage2_normalizer.apply_cost_guard()`：在归一化阶段把不达标方案降级为「不下单」，
   写入 `cost_guard = {applied, reason, original_plan}`，terminal 标为
   `node_id="cost" / label="成本可行性闸门"`；
3. 界面告警行复用连续性守卫那套（`_continuity_override_note` 同时识别两类闸门）；
4. 台账同样记录（`suppressed_by_guard` / `suppressed_reason` / `suppressed_plan`），
   并做反事实结算。

测试：`tests/unit/test_cost_guard_downgrade.py`（7 项，含"降级而非中止"、
"原方案留档"、"关闸门不动"、"校验器不再阻断"），已加入 CI 门禁。
